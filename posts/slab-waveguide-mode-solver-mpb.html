Building a Slab Waveguide Mode Solver: From Lumerical Scripts to Open-Source MPB

Translating a set of Lumerical MODE scripts for a silicon-on-insulator slab waveguide into a Python library built on MPB — the physics, the bugs (one genuinely nasty), and the function-based library that came out the other end.

Silicon Photonics MPB MEEP Waveguides Quantum Transduction Python

Why this project exists

Photonic waveguide design usually starts with the same question: what is the effective index of the guided mode at my operating wavelength? In commercial tools like Lumerical MODE, this is a few lines of script — draw the geometry, call findmodes, read off n_eff. Open-source alternatives like MPB (MIT Photonic Bands) can solve the exact same physics, but the interface is built around a fundamentally different question, and getting from "I have an MPB installation" to "I have a working, trustworthy waveguide solver" takes real work.

This post documents that work: translating a set of Lumerical MODE scripts for a silicon-on-insulator (SOI) slab waveguide into a Python library built on MPB, the bugs that came up along the way (some subtle, one genuinely nasty), and the function-based library that came out the other end.

The physical problem

A slab waveguide — a thin, high-index layer (here, 220 nm of silicon) sandwiched between lower-index cladding (buried oxide below, and either oxide or air above) — supports a discrete set of guided modes: field distributions that stay bound to the core and propagate along the waveguide without radiating away.

Each guided mode is characterized by its effective index, neff — physically, the ratio of how fast a plane wave travels in vacuum to how fast this particular mode's phase advances along the waveguide. It's the single most load-bearing number in integrated photonics: it sets phase matching conditions, coupling lengths, dispersion, and — for the transduction work this solver is ultimately feeding into — how a guided optical mode can be matched to a microwave or mechanical mode in a frequency-conversion scheme.

For a simple three-layer slab, neff must satisfy a transcendental dispersion relation with no closed-form solution in general — which is exactly the kind of problem eigenmode solvers exist for.

Why MPB doesn't just hand you neff

Here's the conceptual crux of the whole project. Lumerical's FDE solver lets you fix a wavelength and directly ask for neff. MPB's eigensolver works the other way around: you give it a propagation constant, k, and it hands you back the frequencies, ω, of every mode that exists at that k. It's a "k in, ω out" tool, not an "ω in, k out" tool.

That mismatch is real physics, not an API quirk — MPB solves Maxwell's equations as a linear eigenvalue problem, and k is the natural parameter of that eigenvalue problem (it sets the periodic boundary phase), while finding the k for an arbitrary target ω requires inverting a relationship that has no closed form.

The picture that makes this concrete is a dispersion diagram — ω plotted against k, bounded by two "light lines":

  • the cladding light line, ω = ck/nclad, above which a mode simply isn't confined (it radiates into the cladding)
  • the core light line, ω = ck/ncore, below which no real mode exists at all

A guided mode's ω(k) curve is trapped in the wedge between these two lines — hugging the cladding line near cutoff, and bending toward the core line as k grows.

Figure: dispersion diagram k on the x-axis, ω on the y-axis, light lines dashed, mode curve solid, target-ω horizontal line, kcross marked.

The solution: since MPB gives you ω(k), sweep k across a physically bounded range (between the two light lines), then root-find for the k where the resulting curve crosses your target frequency. That crossing point, divided by the target frequency, is neff. It's a small amount of extra machinery around MPB's native output, but it's exactly what's needed to answer the question you actually have.

The debugging story

Getting the physics conceptually right was the easy part. Getting the implementation right took considerably longer, and the bugs along the way are worth documenting — partly as a record for future me, partly because they're genuinely instructive about the difference between "the code runs" and "the code is correct."

Bug 1: the axis order wasn't what I assumed

get_efield() returns a NumPy array, and I initially assumed the standard (x, y, z, component) ordering. A field profile that should have spanned thousands of grid points along z came back as a single point — the indexing was silently grabbing the wrong axis. A debug print of the raw array shape ((4116, 1, 1, 3)) settled it: the true order is (z, y, x, component). The fix — np.squeeze() to drop the size-1 axes regardless of position — sidesteps the need to hardcode an assumption about ordering at all.

Bug 2: two "different" modes with identical neff

At one point, two physically distinct modes (quasi-TE and quasi-TM, with visibly different field profiles) reported identical neff to five decimal places. The cause was a classic Python scoping trap: a loop variable (k_cross) from an earlier loop was being silently reused in a later loop, because the later loop's own recomputation of neff was redundant and referenced stale state instead of the already-correct value passed in. The fix was one line — delete the redundant recomputation — but finding it meant tracing the actual solver log output line by line to rule out a physics problem first.

Bug 3: the one that actually mattered — periodic boundary wraparound

This was the real one. MPB has no PML (perfectly matched layer) — unlike Lumerical's FDE solver, its computational cell is strictly periodic. That's a fine approximation if the cell is large enough to contain the full geometry, but if it isn't, the layers don't get truncated — they wrap around and physically overlap with each other.

The symptom: a call to get_epsilon() showed a mystery dielectric value of 6.455 in the profile — a number that didn't correspond to any of the actual materials (air = 1.0, SiO₂ = 2.085, Si = 12.11). That value was the subpixel-averaged blend of two materials whose periodic images had been folded on top of each other, because the cladding layers were larger than the cell that was supposed to contain them.

The fix ended up being a specific formula: size the computational cell symmetrically around the core, using twice the larger of the two cladding thicknesses — not their sum, and not an arbitrary fixed margin: 

def _sim_cell_z(cfg):
    half_cell = max(cfg["thick_BOX_um"], cfg["thick_Clad_um"]) + cfg["thick_Si_um"] / 2
    return 2 * half_cell

This single function is probably the most important line in the whole library — get it wrong, and every downstream result (neff, mode shape, convergence behavior) can be silently corrupted without throwing a single error.

Bug 4: a scaling mistake that looked like real physics

While comparing mode-profile decay against a textbook reference, the simulated field appeared to decay noticeably slower than expected — which looked like it could be a real confinement/geometry issue worth chasing. It turned out to be a plotting bug: np.log(intensity/10) instead of the correct decibel convention, 10 * np.log10(intensity / np.max(intensity)). Natural log versus base-10, and a missing factor of 10, compressed the apparent decay slope by roughly 4.3× — a purely cosmetic error that looked exactly like a physical discrepancy until traced back to the axis math.

The general lesson across all four of these: when a result looks wrong, check the plumbing before the physics. Three of these four bugs had nothing to do with electromagnetics at all.

The final design: functions, not objects

An earlier version of this library used a dataclass-based config object and dedicated result classes for solves and sweeps. It worked, but added a layer of vocabulary (config objects, sweep-result objects) between "I want to change one parameter and re-solve" and actually doing it — which matters a lot for a tool meant to support fast, exploratory parameter sweeps.

The current version is built around one idea: every setting is a keyword argument with a default, held in a single DEFAULTS dictionary, and every function accepts overrides on top of it. 

DEFAULTS = dict(
    thick_Si_um=0.22, thick_BOX_um=2.0, thick_Clad_um=3.0,
    n_Si=3.48, n_SiO2=1.44, n_Clad=1.44, n_Air=1.0,
    wavelength_um=1.55,
    resolution=1000, num_modes=2, tolerance=1e-15, n_kpoints=120,
)

result = solve_neff()                      # everything at default
result = solve_neff(thick_Si_um=0.25)      # override just one thing

Sweeping — the actual point of the exercise — becomes a one-liner rather than a duplicated solve loop: 

swept = sweep("thick_Si_um", np.linspace(0.18, 0.26, 9))
grid  = sweep_grid({"thick_Si_um": [0.20, 0.22, 0.24],
                     "wavelength_um": np.linspace(1.5, 1.6, 11)})

Both are thin wrappers that call solve_neff() in a loop, changing one keyword each time — no sweep-specific class to learn, and every function signature is self-documenting via help() or Jupyter's shift-tab.

Convergence testing

Since MPB has no PML, "does this result actually mean anything" isn't a rhetorical question — it needs a real convergence check, the same way a Lumerical mesh-accuracy sweep would. Two axes matter here:

  • Resolution (grid points per micron) — standard mesh convergence.
  • Padding (cladding thickness / cell size) — MPB-specific, since this is exactly the axis that governs periodic-boundary wraparound (Bug 3, above). A padding sweep that shows large relative changes at small padding and stabilizes as padding increases is direct confirmation the geometry is being solved correctly, not corrupted by the periodic boundary.

What's next

This library is deliberately scoped to a 1D vertical slab problem — it captures the vertical layer stack but not lateral ridge-width confinement, matching the simplified "1D Z:X propagation" solve type this project started from. Extending it to a true 2D ridge/strip waveguide cross-section is the natural next step, along with wrapping the whole thing in a small web front-end (FastAPI + a background job queue, since MPB solves are slow enough to need async handling) so labmates can run sweeps without touching Python directly.
